# Collections Online SEO Options

## Context

Collections Online is currently delivered as a client-side React widget embedded into four separate museum sites. Each museum site is CMS-driven and runs on Drupal 7.

The current frontend uses client-side routing and renders most meaningful page content after JavaScript has loaded. This limits search engine visibility, particularly for catalogue item pages, which are the highest-priority SEO target.

The current Collections Online experience lives under the `/collections-online` route on each museum site. For example, Ashmolean search currently lives at `https://ashmolean.org/collections-online#/search`.

The goal is to make catalogue content crawlable while avoiding unnecessary disruption to the existing embedded search experience.

## Museums

- Ashmolean Museum: `https://ashmolean.org/`
- The Museum of Natural History: `https://www.nhm.ac.uk/`
- Pitt Rivers Museum: `https://www.prm.ox.ac.uk/`
- Museum of the History of Science: `https://www.hsm.ox.ac.uk/`

## Goals

- Make catalogue item pages indexable by Google.
- Generate stable, crawlable URLs for catalogue records.
- Generate `sitemap.xml` entries for catalogue items.
- Preserve the current search experience while a new frontend is developed.
- Preserve the ability for CMS pages to embed smaller Collections Online widgets.
- Support all four museums with clear isolation between deployments.
- Deploy to AWS.

## Assumptions

- Next.js is the preferred framework for the SEO-facing application.
- The existing Collections Online API remains the source of catalogue data.
- Each museum can be hosted on its own subdomain.
- Drupal 7 remains in place for the surrounding museum websites.
- The existing React widget continues to support embedded widgets and search during any phased delivery.
- Some Collections Online pages include CMS-managed Drupal content around the current embedded widget, and this content needs a migration or reuse strategy.
- Drupal pages can currently include small HTML placeholders that conditionally render specific Collections Online React widgets inside CMS-authored pages.

## Recommended Direction

The lowest-risk route is a phased Next.js build focused first on catalogue item pages, with the aim of iterating towards the full Next.js rebuild over time.

In phase one, build a new Next.js application for catalogue item pages only, deployed on museum-specific subdomains. The existing Collections Online frontend remains in place for search and embedded widgets. Search result links are updated so catalogue item clicks go to the new crawlable Next.js item pages.

This gives the main SEO benefit early without forcing a full rebuild of search, filters, browse pages, embedded widgets, and museum-specific presentation in one delivery.

The recommended phase one delivery is:

- Build crawlable Next.js item pages.
- Update existing search result links to point to the new item pages.
- Backend-owned sitemap generation from the indexing stack.
- Defer dynamic headers, footers, and CMS-driven item-page content for a later decision.
- Existing `/collections-online` pages and CMS-embedded widgets retained during migration.

This is the quickest route to SEO value while keeping the current Collections Online experience operational.

Before committing to the full phase one implementation, deliver a very small proof of concept: a handful of basic Next.js item pages, a simple sitemap XML file, and a small number of links from the existing frontend pointing to those pages. The purpose of the POC is to prove that Google can discover, crawl, and index the new URL pattern before scaling up to the full catalogue.

## Option 1: Catalogue Item Pages First

Build a new Next.js application that only serves catalogue item detail pages at first.

Example structure:

- Existing search stays at `https://ashmolean.org/collections-online#/search`.
- A catalogue item moves to a new subdomain, for example `https://co.ashmolean.org/item/387563/attic-red-figure-cup-depicting-theseus-and-the-minotaur`.
- The route shape should be `/item/:object-id/:slug?`, where the object ID is the resolver and the slug is only used for readability and canonicalisation.

The current React frontend stays embedded in Drupal and continues to handle search, browse, filters, related content, and widgets. Search result item links are changed to point to the relevant Next.js subdomain.

### Pros

- Delivers the highest-value SEO improvement first.
- Much smaller initial scope than a full rebuild.
- Keeps the existing search and widget behaviour stable.
- Avoids rebuilding complex filters, browse flows, exports, selections, and embedded widgets immediately.
- Allows each museum to be isolated on its own subdomain.
- Catalogue item pages can use ISR so records are fast, cacheable, and periodically refreshed.
- Sitemaps can be generated by the existing indexing backend from the final indexed catalogue state.
- Lower delivery risk because the current frontend remains the operational fallback.
- Gives the team a production Next.js/AWS pattern before moving more of the product across.

### Cons

- Users move between the existing Drupal-embedded frontend and the new Next.js item pages.
- The experience may feel split unless visual design, headers, footers, and navigation are aligned.
- Search result URLs must be carefully updated for all museums and embedded contexts.
- Back/search navigation needs deliberate handling so users can return from item pages to their previous search.
- Analytics will need to be joined across the existing frontend and the new subdomain.
- Some duplicate rendering logic may exist temporarily between the old React item templates and the new Next.js item pages.
- The public URL format needs a stable object identifier so pages can still resolve if titles or slugs change.

### Notes

This is the strongest first phase if catalogue item visibility is the priority. It avoids letting the perfect full rebuild block the SEO win.

This can either be treated as phase one of a wider migration, or as a narrower SEO-only project if catalogue item indexing is the only requirement. The technical delivery is largely the same; the strategic difference is whether the existing React frontend is expected to remain long-term.

## Option 2: Full Next.js Rebuild On Subdomains

Rebuild the whole Collections Online frontend as a Next.js app. Each museum gets a separate deployment or runtime configuration on its own subdomain.

The Next.js app would replace the current embedded React app for search, catalogue item pages, browse pages, related content, and other Collections Online routes.

### Pros

- Clean long-term architecture.
- All key routes can be crawlable where appropriate.
- Removes reliance on client-side hash routing for the main Collections Online experience.
- Reduces the long-term need to maintain two frontends.
- Easier to build consistent metadata, canonical URLs, structured data, and sitemap references across the whole product.
- Clear separation from Drupal 7 while still allowing Drupal to own the main museum websites.
- Good fit for ISR, especially for catalogue item pages and stable browse/listing pages.

### Cons

- Highest delivery cost and highest delivery risk.
- Requires rebuilding search, filters, pagination, browse pages, item pages, museum-specific templates, analytics, exports, selections, and related item flows.
- More regression risk across four museums.
- Requires a larger acceptance testing effort because the current frontend contains several museum-specific behaviours.
- Delays the catalogue item SEO benefit until a much larger body of work is complete.
- Embedded widgets still need a strategy, because Drupal pages currently rely on this frontend for widget-style content.

### Notes

This is likely the correct end state, but it is probably too large to treat as the first SEO delivery unless there is appetite for a wider product rebuild.

## Embedded CMS Widgets

The current frontend does not only render the main Collections Online application. It also supports smaller React widgets that Drupal editors can place into CMS pages using specific HTML containers and `data-*` attributes.

Current examples include:

- Search result grids mounted into `.collections-online-search-results-grid`.
- Single item thumbnails mounted into `.collections-online-single-item-container`.
- Object groups mounted into `.collections-online-object-group`.
- Dynamic content replacement driven by `window.dynamicContent`, where original CMS content can be hidden once the widget starts.

This capability should be retained.

Under Option 1, this is straightforward because the current frontend remains in place for search, browse, and embedded widget use. The new Next.js item pages do not need to replace these widgets during phase one.

Under Option 2, a full rebuild should still preserve an embeddable widget strategy. That could mean keeping a small standalone widget bundle alongside the Next.js app, rebuilding the widgets as isolated Next.js/React entry points, or deliberately leaving the existing widget bundle in place for Drupal CMS embeds while the main Collections Online experience moves to Next.js.

The important point is that a full Next.js rebuild should not accidentally remove the museums' ability to add Collections Online-powered content into normal CMS pages.

## Drupal Content, Headers And Footers

Because the museum sites are Drupal 7-driven, the Next.js app needs a way to present museum-specific headers, footers, navigation, and any CMS-managed Collections Online content that currently appears around the embedded widget.

This is separate from the main frontend decision. Both option 1 and option 2 need a solution for this.

### Approach A: Scrape The Rendered Drupal Page

Fetch the existing Drupal-rendered Collections Online page for each museum, parse it with a server-side HTML parser such as Cheerio or JSDOM, and extract the required page regions.

This could include:

- Header.
- Footer.
- Primary navigation.
- Secondary navigation where needed.
- CMS-managed content above or below the current Collections Online widget.
- Any per-museum page furniture that needs to appear on the new subdomain.

The extracted content can then be cached and served by Next.js.

#### Pros

- Uses the existing Drupal output as the source of truth.
- Avoids new Drupal development initially.
- Preserves CMS-managed content without manually rebuilding every field and menu.
- Likely fastest if the existing rendered page already contains everything needed.
- Useful for phase one because it keeps the integration lightweight.

#### Cons

- Fragile if Drupal markup changes.
- Requires reliable selectors for each museum.
- Extracted HTML may include scripts, styles, IDs, or relative links that need cleaning.
- Can accidentally inherit unwanted page markup from Drupal.
- Error handling and fallbacks matter, because a failed scrape should not break item pages.
- It is a bit of a tactical hack, even if it is a useful one.

#### Notes

This is probably the quickest route for phase one. It works best if the Drupal page structure is stable and the extracted regions are cached rather than fetched on every request.

### Approach B: Add A Drupal JSON Service

Add a Drupal-side service or endpoint that returns the required header, footer, navigation, and Collections Online CMS content as structured JSON.

Next.js then renders this data using its own components.

#### Pros

- Cleaner contract between Drupal and Next.js.
- More stable than scraping rendered HTML.
- Lets Next.js control markup, accessibility, performance, and responsive behaviour.
- Easier to test because the data contract is explicit.
- Avoids pulling unwanted Drupal scripts/styles into the Next.js app.
- Better long-term fit if the full Next.js rebuild goes ahead.

#### Cons

- Requires Drupal 7 development.
- Needs agreement on the JSON shape for each museum.
- May expose differences between museum Drupal builds that are currently hidden in templates.
- Next.js must rebuild the header/footer/menu components manually.
- More upfront work than scraping.

#### Notes

This is the better long-term integration. It is more work, but it avoids coupling the new frontend to Drupal markup, which is where the pain usually turns up later, the sneaky little shit.

### Approach C: Drupal-Rendered HTML Fragments

Add Drupal endpoints that return only the rendered page fragments needed by Next.js, rather than returning the full page or raw JSON.

For example:

- Header HTML.
- Footer HTML.
- Menu HTML.
- Collections Online intro/body content.
- Content that currently appears below the embedded widget.

Next.js fetches these fragments, cleans or normalises them where needed, and renders them inside the page shell.

#### Pros

- Less brittle than scraping a whole Drupal page.
- Less frontend rebuild work than a pure JSON service.
- Keeps Drupal templates as the source of presentation for CMS-owned regions.
- Preserves editor-managed content without duplicating it in Next.js.
- Can be cached in the same way as scraped content.

#### Cons

- Still couples Next.js to Drupal-generated markup.
- Requires Drupal work to expose clean fragment endpoints.
- HTML fragments need careful sanitisation and link rewriting.
- Styling may still depend on Drupal CSS unless the fragments are kept deliberately simple.
- Accessibility and responsive behaviour can be harder to enforce than with native Next.js components.

#### Notes

This is a strong compromise if Drupal development is available but a full JSON contract feels too slow. It avoids parsing a full page while still letting Drupal own CMS-managed markup.

### Approach D: Static Export From Drupal

Create a scheduled Drupal-side export that writes the required header, footer, menu, and page content into JSON files. Next.js reads those files from S3 or another stable location.

#### Pros

- Keeps runtime coupling low.
- Next.js does not need to call Drupal during page rendering.
- Failures are easier to isolate because the last successful export can remain in use.
- Works well with scheduled rebuilds and ISR.

#### Cons

- Still requires Drupal-side work.
- Content freshness depends on the export schedule unless there is manual invalidation.
- Adds another moving part to monitor.
- Editors may not immediately see menu/content updates reflected on the Next.js subdomain.

#### Notes

This is a good compromise if live Drupal APIs are awkward but scraping feels too brittle.

### Approach E: Manually Managed Next.js Content

Rebuild the required headers, footers, menus, and Collections Online page content directly in the Next.js app using static configuration or a small content source outside Drupal.

#### Pros

- Simple runtime model.
- No dependency on Drupal availability.
- Full control over output.
- Can be acceptable if the required content changes rarely.

#### Cons

- Duplicates content that editors currently manage in Drupal.
- Creates an editorial process outside the existing CMS.
- Menu and footer changes can drift from the parent museum sites.
- Not ideal for four museums unless content is genuinely stable.

#### Notes

This should only be used for content that is stable and low-risk. It is not a good replacement for CMS-managed navigation unless the museums are comfortable owning that duplication.

### Approach F: Independent Static Header/Footer And No CMS Content

Do not integrate with Drupal for the catalogue item pages at all. Instead, create a specific static header and footer for each museum inside the Next.js app, and either omit any additional CMS-driven Collections Online content or replace it with manually maintained static content.

This could be done in two ways:

- Build a relatively seamless museum-branded header/footer that feels similar to the parent museum site.
- Build a simpler, clearly independent Collections Online header/footer that does not try to closely mirror the museum site.

For content that currently appears above or below the embedded Collections Online widget, decide whether it can become static per museum. If it cannot be static, it should be omitted from catalogue item pages unless a Drupal scraping, fragment, or JSON approach is chosen.

#### Pros

- Fastest route if the priority is getting crawlable catalogue item pages live.
- No dependency on Drupal availability, markup, APIs, or template changes.
- Avoids scraping, sanitising, and rendering external HTML.
- Keeps the Next.js app simple and predictable.
- Makes phase one easier to deliver because item pages can ship without a CMS integration dependency.
- Allows each museum to have its own static content after catalogue items if that content is stable.

#### Cons

- The user journey can feel more jarring in phased delivery.
- Users may move from the museum site, to the existing Drupal-rendered `/collections-online` search page with normal museum header/footer, then to a catalogue item page with a different header/footer.
- Editors lose CMS control over any content shown on the catalogue item pages.
- Header/footer links can drift from the museum site unless manually maintained.
- If the static header/footer tries to look seamless, it still needs design and QA across four brands.
- If the static header/footer is deliberately simple, it may feel less integrated with the parent museum sites.

#### Notes

This is a valid phase one shortcut if the goal is to get item pages indexed quickly and avoid coupling the new app to Drupal. It should be an intentional product decision, not an accidental omission. The main trade-off is editorial flexibility and visual continuity.

### Recommended Content Approach

For phase one, use Approach F if speed and low coupling are the priority, and the museums are comfortable with static or omitted post-item content.

If the catalogue item pages need to feel closer to the current museum sites without Drupal development, use Approach A: scrape the rendered Drupal page, cache the extracted regions, and add strong fallbacks.

If there is some Drupal capacity, Approach C is probably the best compromise: expose clean rendered fragments rather than scraping full pages.

If this needs to become a long-term platform direction, create a JSON export or service early. That gives Next.js the cleanest contract and avoids a future migration away from Drupal-generated markup.

Whichever approach is chosen, the implementation should:

- Cache any Drupal-sourced content in the Next.js/AWS layer.
- Refresh Drupal-sourced content on a scheduled job.
- Rewrite relative links and asset URLs safely if external HTML is used.
- Strip or control Drupal scripts before rendering inside Next.js if external HTML is used.
- Keep a safe fallback for temporary Drupal/API failures.
- Test output across all four museum brands.

## AWS Deployment

The preferred deployment target is AWS.

Recommended AWS approach:

- Deploy the Next.js app using OpenNext.
- Use CloudFront in front of the app.
- Use S3 and Lambda/Lambda@Edge as required by the chosen OpenNext architecture.
- Use Route 53 or existing DNS management for museum-specific subdomains.
- Use the existing backend indexing process for sitemap generation, with scheduled jobs for header/footer refreshes.
- Store museum-specific configuration in environment variables or AWS-managed configuration.

Next.js 16.2 introduced a stable Adapter API, intended to give hosting providers a public contract for deploying Next.js consistently across platforms. OpenNext has been part of that work and is currently the practical AWS deployment route, but adapters for AWS through OpenNext are in active development. The plan should therefore be to use OpenNext initially, then review and swap to native AWS adapter support when it becomes available and production-ready.

### Pros

- Keeps infrastructure within AWS.
- Avoids tying the project to Vercel if that is not acceptable.
- OpenNext provides a practical deployment path for ISR-style Next.js applications on AWS.
- The stable Next.js Adapter API gives a clearer migration path away from deployment-specific workarounds over time.
- Can align with existing AWS hosting, monitoring, logging, and security practices.

### Cons

- More operational complexity than Vercel.
- Preview deployments and debugging are not as slick out of the box.
- The team needs to own CloudFront caching, invalidation, logs, alarms, and deployment behaviour.
- Native AWS adapter support is not the starting point yet, so the project should plan for a later review and migration rather than blocking delivery on it.

## Sitemap And Indexing Requirements

Museum-specific sitemaps should be generated by the existing backend indexing stack, not by the Next.js frontend at request time.

The collections may contain more than 400,000 catalogue records, so sitemap generation is a data/indexing task rather than a small routing feature. The sitemap source of truth should be the final indexed catalogue state in OpenSearch, because that already reflects publication rules, deletes, validation state, and museum-specific indexing behaviour.

For Ashmolean and Pitt Rivers Museum, sitemap generation can be triggered when the MPlus indexing recursion finishes. For Museum of Natural History and History of Science Museum, indexing currently runs through SQS, so sitemap generation is better handled by a scheduled backend job after indexing unless a more explicit completion tracker is added.

Generated sitemap XML files should be written to public static storage. This repo already defines public per-museum asset buckets such as `ash-online-collections-assets-${stage}`, `prm-online-collections-assets-${stage}`, `hsm-online-collections-assets-${stage}`, and `mhn-online-collections-assets-${stage}`. The `mhn` bucket name appears to be the existing Natural History Museum asset naming used by this codebase. The sitemap generator can upload files under a stable prefix such as `sitemaps/` with `ContentType: application/xml; charset=utf-8`.

The Next.js app should not need to query OpenSearch or generate the large item sitemap files itself. Its role should be to expose a lightweight canonical `sitemap.xml` or `robots.txt` entry for each museum subdomain, pointing at the backend-generated sitemap index files.

The sitemap files may physically live in S3 or another static origin, but search engines should discover them from the public Collections Online host. For example, `https://co.ashmolean.org/sitemap.xml` should return, redirect, or rewrite to a sitemap index that references the generated files. The URLs inside those sitemap files must be the canonical public item URLs, not S3 asset URLs.

Recommended sitemap behaviour:

- Generate backend-owned sitemap XML files per museum.
- Generate sitemap indexes rather than one large sitemap file.
- Split item URLs into batches within search engine limits: maximum `50,000` URLs per sitemap and `50MB` uncompressed per sitemap file.
- Include canonical catalogue item URLs.
- Exclude unpublished, restricted, suppressed, or culturally sensitive records where required.
- Include `lastmod` where the source data supports it.
- Avoid regenerating every sitemap file if only a small set of records has changed.
- Store generated sitemap files in the existing public asset buckets or another static origin behind CloudFront.
- Expose or reference the sitemap index from the relevant Next.js museum subdomain.
- Keep sitemap generation observable, with logs and failure alerts.
- Submit each sitemap in Google Search Console.

Example generated files:

- `sitemaps/sitemap-ash-index.xml`
- `sitemaps/sitemap-ash-1.xml`
- `sitemaps/sitemap-ash-2.xml`
- `sitemaps/sitemap-prm-index.xml`

Example Next.js `sitemap.xml` role:

- Return a small sitemap index that points to the generated static XML files.
- Or redirect/rewrite `/sitemap.xml` to the generated sitemap index.
- Add matching `Sitemap:` entries in `robots.txt`.

Item pages should also include:

- Server-rendered title and description.
- Canonical URL.
- Open Graph metadata.
- Structured data where appropriate.
- Appropriate `robots` handling for unavailable or non-public records.

## Phasing

### Phase 0: Indexing Proof Of Concept

- Build a tiny set of basic Next.js item pages.
- Use static or minimally fetched catalogue data.
- Generate a simple sitemap XML file for the test pages.
- Point a small number of existing search result links at the Next.js pages.
- Confirm the pages can be crawled and indexed.
- Use this to validate the URL shape, metadata, sitemap discovery, and deployment approach before scaling.

### Phase 1: Crawlable Item Pages

- Build Next.js item detail pages.
- Deploy one subdomain per museum.
- Fetch catalogue item data from the existing API.
- Generate item metadata and canonical URLs.
- Update existing search result links to point to the new item pages.
- Add analytics across the new subdomains.
- Use `/item/:object-id/:slug?` as the item route shape.

### Phase 2: Readable Item Slugs

- Use the object ID as the resolver, not the title slug.
- Define the URL pattern as `/item/:object-id/:slug?`.
- Generate the preferred slug from the item title where a usable title exists.
- Convert titles such as `Attic red-figure cup depicting Theseus and the Minotaur` into canonical URLs such as `/item/387563/attic-red-figure-cup-depicting-theseus-and-the-minotaur`.
- If an item has no useful title, use the object ID URL or a safe fallback slug.
- Do not require slugs to be unique across the museum, because the object ID disambiguates the route.
- Allow any old slug to resolve as long as the object ID is valid.
- Set the canonical URL to the current best title-based slug where one can be generated.
- Return a `301` redirect from `/item/:object-id`, `/item/:object-id/:old-slug`, or `/item/:object-id/:anything` to the canonical URL.
- If a title changes, the old URL will still resolve via the object ID and can redirect to the new canonical URL instead of returning `404`.

### Phase 3: Backend-Owned Sitemap Generation

- Build a sitemap generator in the existing backend indexing stack.
- Query OpenSearch for indexable catalogue records by museum.
- Generate museum-specific sitemap indexes.
- Generate item sitemap files in batches suitable for very large collections.
- Include canonical `/item/:object-id/:slug` URLs where a slug can be generated.
- Exclude records that should not be indexed.
- Include `lastmod` where reliable data is available.
- Store generated sitemap files in public static storage, ideally the existing per-museum asset buckets behind CloudFront.
- Trigger generation after MPlus indexing finishes where possible, and schedule it after SQS-based indexing for EMu museums.
- Add logs, failure alerts, and basic validation of generated XML.
- Expose the generated sitemap index from the Next.js subdomain through `/sitemap.xml` or `robots.txt`.
- Ensure sitemap files contain public canonical item URLs on the `co.*` domains, not static asset bucket URLs.
- Submit each museum sitemap in Google Search Console.

### Phase 4: Dynamic Headers, Footers And CMS Content

- Use minimal/static page chrome for the first Next.js item-page delivery unless the museums require more.
- Discuss whether item pages need dynamic museum headers, footers, or CMS-driven content.
- Decide whether the static phase-one presentation is good enough or should be replaced.
- If museums require CMS-driven item-page content, choose a Drupal integration approach: rendered page scraping, rendered fragments, JSON service, or static export.
- Document which CMS-managed content remains available on the existing Drupal-rendered `/collections-online` pages during migration.

### Phase 5: Iterative Route Migration Towards Option 2

- Continue moving routes into Next.js if needed, aiming towards Option 2 in phases rather than as a big-bang rebuild.
- Candidate routes include browse pages, curated landing pages, related item pages, and selected search landing pages.
- Keep highly interactive search client-side unless there is a strong SEO or product reason to rebuild it.
- Rebuild, replace, or retain the embedded CMS widgets so Drupal-authored pages can continue to include Collections Online-powered snippets.
- Remove duplicate item page logic once the Next.js version is proven.

## Decision Summary

There are two main frontend delivery options:

- Option 1: catalogue item pages first.
- Option 2: full Next.js rebuild on subdomains.

The recommended first move is Option 1, delivered as a thin SEO-focused phase.

This means building crawlable catalogue item pages in Next.js on museum-specific subdomains, while leaving the existing Drupal-rendered `/collections-online` experience in place for search, search results, advanced search, browse routes, and embedded widgets.

The MVP delivery should be:

- Build crawlable Next.js item pages.
- Update existing search result links to point to those pages.
- Generate backend-owned sitemaps from the indexing stack.

Dynamic headers, footers, and CMS-driven item-page content should be discussed after this MVP, not treated as a dependency for the first delivery.

The item URL shape should be `/item/:object-id/:slug?`. The object ID resolves the record, and the slug is used for readability and canonical SEO URLs. If the slug is missing, old, or nonsense, the page can still resolve by object ID and `301` redirect to the canonical URL.

Before scaling the implementation, build a small proof of concept with basic Next.js item pages, a simple sitemap XML file, and a small number of links from the existing frontend. Use that to prove Google can discover and index the new pages.

This gives the project the main SEO benefit quickly, keeps delivery risk under control, and avoids coupling the first Next.js release to Drupal scraping or Drupal API work. The longer-term goal can still be Option 2, but it should be reached iteratively in phases rather than attempted as a big-bang rebuild. If Option 2 is later delivered, the embeddable CMS widget capability should remain part of the product, either as a retained standalone bundle or as rebuilt widget entry points.
